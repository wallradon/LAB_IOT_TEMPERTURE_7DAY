PHASE 1

ต้นทางข้อมูล · Hardware & IoT (ESP32)

ด่านหน้าที่สุด — บอร์ดเล็กๆ ที่คอยจับตาดูโลกจริง (วัดอุณหภูมิ วัดความชื้น) แล้วเขียนจดหมายส่งออกไป

เปรียบเทียบง่ายๆ

ลองนึกว่า ESP32 เป็น ทหารยาม ที่ยืนเฝ้าหน้าด่าน: เจออะไรก็จดบันทึก (อ่านเซนเซอร์) แล้วส่งโทรเลข (HTTP POST) ไปให้หัวหน้า ซึ่งระหว่างรอก็แอบหลับประหยัดพลังงาน (Deep Sleep)

ภาษา

C/C++ + Arduino Framework

ภาษาที่ใช้สั่งบอร์ด เช่น ตั้งค่า Wi-Fi, อ่านค่าจากขาเซนเซอร์ เหมือนภาษาเดียวกับเจ้าของบอร์ดใช้พูดคุยกับมัน

เข้าใจวิธีตั้งค่า Wi-Fi และอ่านค่าพิน
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • โค้ด Arduino มี 2 ส่วนตายตัว: setup() รันครั้งเดียวตอนเปิดเครื่อง (ตั้ง Wi-Fi, ตั้งขา) และ loop() รันซ้ำไม่รู้จบ
  • เบื้องหลัง Arduino Framework เรียกใช้ ESP-IDF (SDK ของแท้ของ ESP32) อีกที — เราเขียนภาษาง่ายๆ แต่คอมไพล์เป็นเครื่องจักรจริงๆ
  • Serial.begin(115200) เปิดช่องสื่อสารกับคอมพิวเตอร์ผ่าน USB เพื่อดู Log และค่า Debug
  • pinMode() ตั้งทิศทางของขา digitalWrite() สั่งไฟเปิด/ปิด analogRead() อ่านค่าอนาล็อก

ตัวอย่างโค้ด

void setup() {
  Serial.begin(115200);           // เปิดช่องคุยกับคอม
  WiFi.begin("SSID", "password"); // เชื่อม Wi-Fi
  pinMode(2, OUTPUT);             // ขา 2 = ขาออก (LED)
}

void loop() {
  digitalWrite(2, HIGH);          // เปิด LED
  delay(1000);                    // รอ 1 วิ
  digitalWrite(2, LOW);           // ปิด LED
  delay(1000);
}

จุดที่พลาดบ่อย

  • เปิด Serial Monitor ด้วย Baud Rate ไม่ตรง (ต้อง 115200) จะเห็นตัวหนังสือมั่ว
  • ลืมใส่ delay() ใน loop() → โค้ดทำงานเร็วมากจนรวน (Wi-Fi ยังไม่ทันต่อ)
  • ขา GPIO 34-39 อ่านได้อย่างเดียว ใช้ pinMode(34, OUTPUT) ไม่ได้
วงจร

Digital Logic & Circuits

ขา GPIO คือช่องที่ใช้คุยกัน สัญญาณ High = ไฟเข้า (1) Low = ไม่มีไฟ (0) เหมือนไฟสัญญาณเปิด/ปิด

รู้ว่าเซนเซอร์สื่อสารกับบอร์ดอย่างไร
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • GPIO = General Purpose Input/Output ขาที่ตั้งได้ว่าจะเป็น "ขาอ่าน" หรือ "ขาเขียน"
  • HIGH = แรงดัน ~3.3V (แทนเลข 1) / LOW = 0V (แทนเลข 0)
  • ขาที่ตั้งเป็น INPUT_PULLUP จะมีตัวต้านทานดึงค่าให้เป็น HIGH เอง ป้องกัน "ขาลอย" (Floating) ที่ค่ากระพริบมั่ว
  • ADC (Analog-to-Digital) แปลงแรงดัน 0-3.3V เป็นตัวเลข 0-4095 (12-bit) เช่น เซนเซอร์ความชื้น

ตัวอย่างโค้ด

pinMode(23, INPUT_PULLUP);       // ปุ่มกด — เมื่อกดจะกลายเป็น LOW
bool press = digitalRead(23);    // อ่านค่า: true = ยังไม่กด

pinMode(34, INPUT);              // ขาอนาล็อก 0-3.3V
int raw = analogRead(34);        // ได้ค่า 0 - 4095
float volt = raw * (3.3 / 4095.0); // แปลงกลับเป็นโวลต์

จุดที่พลาดบ่อย

  • ESP32 ใช้ไฟ 3.3V ไม่ใช่ 5V — ต่อ 5V เข้าขาตรงๆ ไหม้บอร์ดได้
  • ปุ่มกดที่ไม่มี Pull-up/Pull-down อ่านค่าได้มั่วเพราะสัญญาณลอย
  • แบ่งแรงดัน (Voltage Divider) ให้ถูกต้องก่อนอ่านค่า ADC
การส่ง

HTTP POST Requests

การห่อข้อมูลเป็น JSON แล้วยิงออกอินเทอร์เน็ต เหมือนเขียนจดหมายในซองพร้อมที่อยู่ปลายทาง

ขั้นตอนแพ็กข้อมูล (Payload) แล้วส่งออก
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • HTTP มีคำสั่งหลัก 4 ตัว: GET (ขอข้อมูล), POST (ส่งข้อมูลใหม่), PUT/PATCH (แก้ข้อมูล), DELETE (ลบ)
  • POST = เอาข้อมูลใส่ใน Body ของคำขอ แล้วเปิดหัวข้อ Content-Type: application/json
  • เซิร์ฟเวอร์ตอบกลับด้วย HTTP Status Code: 2xx = สำเร็จ, 4xx = ผิดฝั่งผู้ส่ง, 5xx = เซิร์ฟเวอร์พัง
  • JSON เป็นรูปแบบข้อความ key: value ที่ทั้งบอร์ดและเซิร์ฟเวอร์อ่านตรงกัน

ตัวอย่างโค้ด

// ใช้ไลบรารี HTTPClient (ติดตั้งผ่าน Library Manager)
#include <HTTPClient.h>
#include <ArduinoJson.h>

HTTPClient http;
http.begin("https://api.example.com/api/data");
http.addHeader("Content-Type", "application/json");

String payload = "{\"temp\":29.5,\"hum\":70}";
int code = http.POST(payload);    // ส่ง! code 201 = บันทึกสำเร็จ
http.end();

จุดที่พลาดบ่อย

  • ลืมตรวจ HTTP code — ส่งไปแล้วไม่รู้ว่าสำเร็จหรือตกหล่น
  • URL ใช้ http:// (ไม่มี s) ถูก Wi-Fi/Library บล็อก เพราะไม่ปลอดภัย
  • สร้าง String payload ด้วยมือง่ายผิดพลาด — ใช้ไลบรารี ArduinoJson ช่วยสร้าง
  • Server ต้องการ Header อย่างอื่น (เช่น API Key) แต่ไม่ได้ส่ง
พลังงาน

Deep Sleep Mode

บอร์ดหลับพักผ่อน แล้วปลุกตัวเองตามเวลา (Timer Wakeup) เพื่อประหยัดแบตเตอรี่ เหมือนตั้งนาฬิกาปลุกแล้วงีบ

ทำไมต้องหลับ และตื่นตามเวลาอย่างไร
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • ESP32 ตอนทำงานใช้ไฟ ~50-150 mA แต่ตอน Deep Sleep เหลือ ~10 µA — ลดลงเป็นหมื่นเท่า ยืดแบตเตอรี่เป็นเดือน/ปี
  • esp_sleep_enable_timer_wakeup() ตั้งนาฬิกาปลุกให้ตื่นเป็นรอบ (วินาที = ไมโครวินาที 1e6)
  • หลับลึกจะปิด CPU และ RAM หลัก ข้อมูลที่อยากเก็บต้องฝากไว้ใน RTC Memory (เหมือนกระเป๋าที่ไม่ทิ้งตอนนอน)
  • นอกจาก Timer แล้ว ปลุกได้ด้วย GPIO (Touch) เช่น กดปุ่มเพื่อปลุก
  • งานใน loop() หยุดทันทีที่หลับ — ต้องออกแบบให้ทำงานเป็น "รอบ" ใน setup()

ตัวอย่างโค้ด

void setup() {
  Serial.begin(115200);
  // ----- 1. ตั้งให้ตื่นทุก 60 วินาที -----
  esp_sleep_enable_timer_wakeup(60 * 1e6);

  // ----- 2. ทำงานที่ต้องทำ -----
  readSensor();
  sendHTTP();

  // ----- 3. หลับลึก -----
  esp_deep_sleep_start();
}

จุดที่พลาดบ่อย

  • ลืมว่าหลังตื่นจะกลับไปรัน setup() ใหม่ ไม่ใช่ loop() ต่อ
  • ตัวแปรปกติหายไปตอนหลับ — ต้องใช้ RTC_DATA_ATTR เก็บค่าที่อยากได้ไว้ข้ามการหลับ
  • ยังเปิด Wi-Fi ค้างไว้ก่อนหลับ → กินไฟโดยเปล่าประโยชน์ ควร WiFi.disconnect() ก่อน
  • 1 จับข้อมูลจากเซนเซอร์ด้วยภาษา C/C++ (setup + loop)
  • 2 รู้จักสัญญาณ High/Low, GPIO, Pull-up, ADC
  • 3 ห่อเป็น JSON แล้ว POST ออกอินเทอร์เน็ต (รอ HTTP 2xx)
  • 4 หลับลึก ~10 µA ปลุกเองเป็นรอบด้วย Timer
PHASE 2

ตัวกลางรับ-ส่งข้อมูล · Backend API (Node.js)

เจ้าหน้าที่รับจดหมายกลางด่าน — รอรับข้อมูลจาก ESP32 แล้ววิ่งไปฝากไว้ในโกดัง

เปรียบเทียบง่ายๆ

Node.js เป็น ไปรษณีย์กลาง: มีหน้าเคาน์เตอร์ (Express route) รับซองจดหมาย แกะซองอ่านเนื้อหา (Middleware) และไม่รอใคร — รับหลายฉบับพร้อมกันได้โดยไม่ติดขัด (Asynchronous)

หัวใจ

JavaScript + Asynchronous

ทำงานแบบไม่ต้องรอคอย — ระหว่างรอข้อมูลของจดหมายฉบับหนึ่ง ก็ไปรับฉบับอื่นต่อได้ เหมือนพนักงานเสิร์ฟที่ลุกไปเสิร์ฟโต๊ะอื่นระหว่างรอครัว

หัวใจสำคัญที่ทำให้ Node.js เร็ว
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Node.js ใช้ Event Loop เธรดเดียว คอยวนรับงานเรื่อยๆ โดยไม่โดน "รอคอย" บล็อก
  • งานช้า (อ่านไฟล์, ส่งคำขอไปฐานข้อมูล) จะถูกส่งไปทำที่ระบบ แล้วจอง Promise ไว้ เมื่อเสร็จแล้ว Event Loop กลับมาทำต่อ
  • เขียนแบบใหม่ๆ ใช้ async / await อ่านง่าย เหมือนเขียนโค้ดทีละบรรทัดธรรมดา แต่ไม่บล็อก
  • Callback คือฟังก์ชันที่ส่งไปให้เรียกตอนเสร็จ — ถ้าโยงเยอะเกิน กลายเป็น "Callback Hell" โค้ดพังอ่านยาก

ตัวอย่างโค้ด

// async = ฟังก์ชันนี้มีงานช้า (รอ DB)
async function handleData(req, res) {
  const row = await db.insert(payload); // อันนี้ "รอ" แต่ไม่บล็อกคนอื่น
  res.json({ ok: true });
}

// เทียบกับแบบ Callback (แบบเก่า ยืดเยื้อ)
db.insert(payload, (err, row) => {
  if (err) return console.log(err);
  res.json({ ok: true });
});

จุดที่พลาดบ่อย

  • มีโค้ดที่บล็อก (Blocking) เช่น while(true) หรือ readFileSync → Event Loop ตายทั้งระบบ
  • ลืม await → โค้ดทำงานต่อก่อนข้อมูลมา ผลลัพธ์ผิด
  • ไม่จัดการ error ใน async → กลายเป็น Promise rejected ที่เงียบ (Unhandled Rejection)
เส้นทาง

Express.js Routing & Middleware

สร้าง API เช่น /api/data สำหรับรับข้อมูล และใช้ Middleware แกะกล่อง JSON เหมือนป้ายบอกเส้นทางในอาคาร + พนักงานตรวจบัตรหน้าประตู

วิธีสร้าง Endpoint และรับ JSON
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Route = เส้นทางที่ประกาศในแอป เช่น POST /api/data แผนที่ HTTP method + path ไปหาฟังก์ชัน
  • Middleware = ฟังก์ชันที่ทำงานก่อนถึงจุดหมาย ทำงานเป็นสายพาน (chained): express.json() แกะ JSON ใน Body ให้เป็น object ก่อนถึง handler
  • req.body เก็บข้อมูลที่ POST เข้ามา (ค่า temp/hum) และ res.status().json() ตอบกลับเป็น JSON พร้อมสถานะ
  • ลำดับของ middleware สำคัญมาก — ต้องประกาศ express.json() ก่อน route ถึงจะใช้ได้

ตัวอย่างโค้ด

const express = require('express');
const app = express();

app.use(express.json()); // middleware: แกะ JSON ทุกคำขอ

app.post('/api/data', (req, res) => {
  const { temp, hum } = req.body; // เอาข้อมูลที่ ESP32 ส่ง
  console.log(`temp=${temp} hum=${hum}`);
  res.status(201).json({ status: 'saved' }); // 201 Created
});

app.listen(3000);

จุดที่พลาดบ่อย

  • ประกาศ app.use(express.json()) หลัง route → body เป็น undefined
  • ต้องจัดการ CORS ถ้าเว็บฝั่ง Browser เรียก API ต่างโดเมน
  • ไม่ validate ข้อมูลก่อน (temp เป็นข้อความ?) → ข้อมูลสกปรกเข้าฐานข้อมูล
ความลับ

Environment Variables (.env)

ซ่อนรหัสผ่านและ API Key ไว้ในไฟล์ลับ ไม่โผล่บนอินเทอร์เน็ต เหมือนกุญแจห้องที่เก็บไว้กับตัว ไม่ติดไว้ที่ประตู

รักษาความปลอดภัยของโค้ด
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • ค่าเซ็นซิทีฟ (รหัสผ่าน DB, API Key, JWT Secret) ไม่ควร Hard-code ในโค้ดที่อาจหลุดขึ้น GitHub
  • .env เป็นไฟล์เก็บค่าเป็น KEY=VALUE และถูก .gitignore กันไม่ให้ commit
  • ไลบรารี dotenv อ่านไฟล์ .env ตอนเริ่มแอป แล้วยัดเข้า process.env
  • ฝั่ง Cloud (Render) ก็กรอกค่าเหล่านี้ใน Dashboard ได้ ไม่ต้องมีไฟล์จริงบนเครื่อง
  • มีไฟล์ .env-template บอกชื่อตัวแปรโดยไม่ใส่ค่าจริง เพื่อให้เพื่อนร่วมทีมสร้าง .env ของตัวเอง

ตัวอย่างโค้ด

// ----- ไฟล์ .env (ห้าม push ขึ้น GitHub!) -----
DB_URL=postgres://user:pass@db.supabase.co:6543/postgres
API_KEY=secret123
PORT=3000

// ----- โค้ด Node.js -----
require('dotenv').config();       // โหลด .env เข้า process.env
const url = process.env.DB_URL;   // ใช้ค่าแบบนี้แทน hard-code
const port = process.env.PORT || 3000;

จุดที่พลาดบ่อย

  • Commit ไฟล์ .env ขึ้น GitHub → รหัสผ่านหลุด ต้องรีบไปแก้รหัสทันที
  • ลืมใส่ .env ใน .gitignore → หลุดทุกครั้ง
  • Hard-code ค่าลับในโค้ดแล้วอัปโหลด → Render สร้าง instance ใหม่ (ตั้งค่า DB_URL ใหม่) แต่โค้ดยังใช้ค่าเก่า
ความจำ

Git & GitHub + Cloud Hosting

Git คือเครื่องย้อนเวลาให้โค้ด (Commit/Push) GitHub คือตู้เก็บผลงาน Cloud (Render) คือเครื่องจักรที่ไปดึงโค้ดมารันเป็นเซิร์ฟเวอร์จริง

ควบคุมเวอร์ชัน และเอาโค้ดขึ้น Cloud
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • git init เริ่มควบคุมเวอร์ชันในโฟลเดอร์ → git add . เอาคนมาเข้างาน → git commit -m "..." ถ่ายรูปโค้ดเป็นจุดย้อนกลับ → git push อัปขึ้น GitHub
  • ทุก commit เก็บประวัติทั้งหมด — เหมือน Save Point ในเกม ย้อนกลับมาเมื่อไหร่ก็ได้
  • .gitignore บอกว่าไฟล์ไหนไม่ต้องติดตาม (node_modules, .env)
  • PaaS (Render): เชื่อม GitHub Repo → กำหนด Build/Start command → มันดึงโค้ด ลง npm install แล้วรันเป็น URL สาธารณะ
  • Time to Live: Render อาจ "หลับ" เมื่อไม่มี traffic (Free tier) — ปกติได้ HTTP response ประมาณ Sleep แรกช้า แต่กลับมาทำงานเอง

จุดที่พลาดบ่อย

  • Commit node_modules ขึ้นไป → repo โต ยาก maintenance
  • Commit ข้อมูลลับ (ไม่มี .gitignore) → ต้องแก้ด้วย git filter + รีเซ็ตรหัส

  • 4 git commit → push → Render auto-deploy
PHASE 3

โกดังเก็บข้อมูล · Database (Supabase)

ที่เก็บข้อมูลทุกอย่างอย่างเป็นระเบียบ — ข้อมูลทุกค่าเก็บลงชั้นวางเรียงตามเวลา ไม่หาย ไม่ปนกัน

เปรียบเทียบง่ายๆ

Supabase (PostgreSQL) คือ ห้องสมุด: ข้อมูลแต่ละค่าเป็นหนังสือบนชั้น (ตาราง/Table) ทุกเล่มมีเลขเรียก (ID + เวลา) และเวลาเปิด-ปิดห้องเป็นเวลามาตรฐานโลก (UTC) ใครจะดูจากที่ไหนก็ตรงกัน

โครงสร้าง

Relational Database (PostgreSQL)

เก็บข้อมูลเป็นตาราง: คอลัมน์ = ประเภทของข้อมูล (Float, Timestamp) แถว = ข้อมูล 1 ชุด เหมือนตารางบันทึกในสมุดเล่มใหญ่

ออกแบบตาราง Row / Column / Data Types
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Table = ตาราง, Column = ชนิดข้อมูลแต่ละช่อง (เช่น temp), Row = ข้อมูล 1 ชุดจากเซนเซอร์ 1 ครั้ง
  • Primary Key = ตัวเลขประจำตัวที่ไม่ซ้ำใคร (SERIAL/BIGSERIAL) ใช้ค้นหาและอ้างอิง
  • Foreign Key = ชี้ไปหาแถวในอีกตาราง เชื่อมความสัมพันธ์ (เช่น device → sensor_data)
  • Data Types ที่เจอบ่อย: FLOAT/REAL (เลขทศนิยม), INTEGER, TEXT/VARCHAR, TIMESTAMPTZ (เวลา), BOOLEAN

ตัวอย่างโค้ด

CREATE TABLE sensor_data (
  id         BIGSERIAL PRIMARY KEY,  -- เลขอัตโนมัติ ไม่ซ้ำ
  device_id  TEXT NOT NULL,
  temp       FLOAT NOT NULL,         -- ชนิด: ตัวเลขทศนิยม
  hum        FLOAT,
  created_at TIMESTAMPTZ DEFAULT NOW() -- เวลาอัตโนมัติ
);

จุดที่พลาดบ่อย

  • เลือก Data Type ผิด (ใช้ TEXT เก็บอุณหภูมิ) → query หาค่ามาก/น้อยไม่ได้
  • ไม่ตั้ง Primary Key → ข้อมูลซ้ำคุมไม่ได้
  • ลืม index บนคอลัมน์ที่ใช้ WHERE บ่อย → query ช้าเมื่อข้อมูลเยอะ
ภาษา

SQL Commands

INSERT = เพิ่มข้อมูลใหม่ SELECT = ดึงข้อมูลออกมา ใช้คู่กับภาษาไทยจริงๆ ก็คือ "จดลงสมุด" กับ "เปิดหน้าอ่าน"

ทบทวนคำสั่งพื้นฐาน INSERT / SELECT
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • INSERT INTO = เพิ่มแถวใหม่ ต้องระบุคอลัมน์กับค่า
  • SELECT = ดึงข้อมูล + WHERE กรอง + ORDER BY เรียง + LIMIT จำกัดจำนวน
  • WHERE คล้ายตัวกรองใน Excel — ค่าไหนตรงเงื่อนไขถึงถูกเลือก
  • ใน Node.js ใช้ Parameterized Query ($1) แทนการต่อ string กัน SQL Injection

ตัวอย่างโค้ด

-- เพิ่มข้อมูล (INSERT)
INSERT INTO sensor_data (device_id, temp, hum)
VALUES ('esp32-01', 29.5, 70);

-- ดึงข้อมูล (SELECT) 10 แถวล่าสุด
SELECT temp, hum, created_at
FROM sensor_data
ORDER BY created_at DESC
LIMIT 10;

-- กรองเฉพาะอุณหภูมิเกิน 30
SELECT * FROM sensor_data WHERE temp > 30;

จุดที่พลาดบ่อย

  • ต่อค่าลง query ตรงๆ (SQL Injection) — ต้องใช้พารามิเตอร์ $1, $2 เสมอ
  • ลืม WHERE ตอน DELETE/UPDATE → ลบ/แก้ทั้งตาราง!
  • ใช้ SELECT * ไม่จำกัด → ดึงข้อมูลเยอะเกินเปลือง
เวลา

Timezones & UTC

ทุกคนบน Cloud ใช้เวลามาตรฐานโลก (UTC) เดียวกัน แปลงเป็น TIMESTAMPTZ เพื่อไม่ให้สับสน เหมือนทุกประเทศคุยกันด้วยเวลากรีนิช

ทำไมต้องเก็บเวลาแบบ UTC เสมอ
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • UTC = เวลามาตรฐานโลก ไม่มีเวลาไทย-เวลาอเมริกาให้สับสน (ไม่มี Daylight Saving)
  • TIMESTAMP ธรรมดา = เก็บตัวเลขเปล่าๆ ไม่รู้ว่าอยู่โซนไหน → ตีความผิดพลาด
  • TIMESTAMPTZ = เก็บช่วงเวลาที่แม่นยำ (เป็น UTC ข้างใน) แล้วตอนอ่านค่อย AT TIME ZONE แปลงเป็นโซนที่ต้องการ
  • หลักการ: เก็บเป็น UTC ตอนเขียน → แปลงตอนอ่าน เพื่อให้คนดูจากที่ไหนเข้าใจตรงกัน

ตัวอย่างโค้ด

-- ดูเวลาปัจจุบัน (ผลเป็น UTC เสมอ)
SELECT NOW();

-- แปลงเป็นเวลาไทย (UTC+7) ตอนอ่าน
SELECT created_at AT TIME ZONE 'Asia/Bangkok'
FROM sensor_data;

-- CAST: เปลี่ยนจาก text เป็น timestamptz
SELECT '2026-08-15 08:00:00+07'
       ::timestamptz;

จุดที่พลาดบ่อย

  • เก็บ TIMESTAMP แบบไม่มี timezone → ค่าเลื่อนเวลา 7 ชม. ทุกครั้ง
  • อยากได้เวลาไทยแต่ลืม AT TIME ZONE → ดูผิดชั่วโมง
  • ตั้งค่า timezone ของเซิร์ฟเวอร์ตามใจ → แสดงผลเพี้ยนข้ามโซน
ท่อส่ง

Connection Pooling (Port 6543)

จัดการท่อเชื่อมต่อฐานข้อมูล ใช้ท่อที่มีอยู่แชร์กันหลายคน แทนที่จะเปิดท่อใหม่ทุกครั้ง เหมือนรถเมล์ที่ไปถึงปลายทางในเที่ยวเดียวพาคนหลายคน

รองรับการเชื่อมต่อจำนวนมากไม่ล่ม
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • ทุกครั้งที่ query = เปิด TCP connection ใหม่ (ช้า + เปลือง resource ฝั่ง DB)
  • Pool = เตรียมท่อเชื่อมต่อสำเร็จไว้ล่วงหน้าแล้ว แชร์ใช้ร่วมกัน กับทุก request
  • Supabase ให้ Port 6543 เป็น PgBouncer Pooler — ทำหน้าที่รับเชื่อมต่อจำนวนมหาศาล แล้วแชร์ท่อน้อยๆ ไปหา DB จริง
  • ปรับ max = จำนวนท่อสูงสุดที่ pool มี เช่น 10 และ idleTimeoutMillis = ปลดท่อว่างทิ้ง

ตัวอย่างโค้ด

const { Pool } = require('pg');
const pool = new Pool({
  connectionString: process.env.DB_URL, // port 6543
  max: 10,                // ท่อสูงสุด 10 ท่อ
  idleTimeoutMillis: 30000
});

app.post('/api/data', async (req, res) => {
  await pool.query(
    'INSERT INTO sensor_data (temp) VALUES ($1)',
    [req.body.temp]
  );
  res.status(201).json({ ok: true });
});

จุดที่พลาดบ่อย

  • เปิด client ใหม่ทุก request แล้วไม่ปิด → FATAL: too many connections
  • ลืมปล่อย client กลับ pool (release) → ท่อหมด
  • ต่อ port 5432 ตรงๆ (ไม่ผ่าน pooler) เมื่อมีคนเยอะ → เกิน limit ของ Supabase
  • 1 ข้อมูลเรียงเป็นตาราง (Table/Row/Column + Data Types)
  • 2 INSERT เพิ่ม / SELECT ดึงข้อมูล + WHERE
  • 3 เก็บเวลาเป็น TIMESTAMPTZ (UTC) ตอนอ่านค่อยแปลง
  • 4 ใช้ Pool + PgBouncer (port 6543) รองรับคนจำนวนมาก
PHASE 4

ปลายทาง · Data Visualization (Grafana)

แปลงตัวเลขดิบๆ ให้เป็นกราฟสีสวย ที่มนุษย์อย่างเราเข้าใจได้ในพริบตา

เปรียบเทียบง่ายๆ

Grafana คือ คนวาดกราฟ: ไปเปิดสมุดในห้องสมุด (เชื่อมต่อ Supabase) อ่านค่าอุณหภูมิแต่ละช่วงเวลา แล้วขีดเป็นเส้นกราฟ ใส่สีเขียว/เหลือง/แดงบอกว่าโอเคหรืออันตราย

การต่อ

Data Sources

เชื่อมต่อกับฐานข้อมูลภายนอกอย่างปลอดภัยด้วย SSL/TLS แบบ require เหมือนสวมกุญแจมือ+เซ็นเซ็นก่อนเข้าห้องเก็บของ

ต่อข้อมูลอย่างปลอดภัย
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Data Source = คำนิยามว่า Grafana จะไปเอาข้อมูลจากไหน (PostgreSQL, InfluxDB, Prometheus...)
  • ขั้นตอน: Administration → Data Sources → Add → PostgreSQL → กรอก Host/DB/User/Password
  • SSL Mode: require = บังคับให้เชื่อมต่อแบบเข้ารหัส (TLS) — ข้อมูลระหว่าง Grafana ↔ Supabase ไม่ถูกดักอ่านกลางทาง
  • บางครั้งต้อง Allow IP ของ Grafana ใน Supabase เพื่อปลดล็อกการเข้าถึง

ขั้นตอน

Grafana > Administration > Data sources
  > Add data source > PostgreSQL

Host      : db.xxx.supabase.co
Database  : postgres
User      : postgres
Password  : ********
SSL Mode  : require    <-- ต้องใส่!

จุดที่พลาดบ่อย

  • SSL Mode เป็น disable → Supabase ตัดการเชื่อมต่อ (หรือข้อมูลไม่เข้ารหัส)
  • ใส่ Port ผิด (ควร 5432 หรือ 6543 ตามแบบ) → connect timeout
  • ลืม Allow IP ของ Grafana Cloud → Denied
เวลา

Time-series Data

ข้อมูลที่ผูกติดกับเวลา — บันทึกค่าทุกช่วงเวลาต่อเนื่อง เหมือนบันทึกน้ำหนักทุกเช้า แล้วดึงดูแนวโน้มได้

ข้อมูลเกิดตามเวลาที่ผ่านไป
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Time-series = คู่ของ (เวลา, ค่า) ที่เกิดต่อเนื่อง เช่น (09:00, 29.5), (09:01, 29.7)...
  • Grafana ส่งช่วงเวลาที่ผู้ใช้เลือก (time range) ผ่าน Macro: $__timeFilter(col) เติม WHERE ให้อัตโนมัติ
  • ข้อมูลจำนวนมหาศาลต้อง Downsample (หั่นเป็นช่วงเวลา) ด้วย $__timeGroup(col, '1h') เพื่อให้กราฟลื่น
  • คอลัมน์เวลาต้องเป็น TIMESTAMPTZ และตั้งชื่อ alias ว่า time ให้ Grafana รู้จัก

ตัวอย่างโค้ด

SELECT
  created_at AS time,          -- Grafana ต้องเจอคอลัมน์ "time"
  temp AS value
FROM sensor_data
WHERE $__timeFilter(created_at)  -- ช่วงเวลาที่เลือกใน Dashboard
ORDER BY time;

จุดที่พลาดบ่อย

  • ตั้งชื่อคอลัมน์เวลาไม่ใช่ time → Grafana ไม่รู้จะวาดแกนไหน
  • ใช้ TIMESTAMP (ไม่มี tz) → เวลาเลื่อนตามโซน Grafana
  • ไม่ downsample → ข้อมูลหมื่นจุด ดึงมาแล้วกราฟช้าหรือ crash
คำสั่ง

Advanced SQL in Grafana

เขียน Query ดึงเวลาคู่กับอุณหภูมิ คำนวณ AVG (ค่าเฉลี่ย) MAX MIN เพื่อวาดกราฟ เหมือนสั่ง "เอาอุณหภูมิตอนเที่ยงทุกวันมา"

ใช้ SQL ทำกราฟ + หาค่าทางสถิติ
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • AVG() ค่าเฉลี่ย, MAX() ค่าสูงสุด, MIN() ค่าต่ำสุด — Aggregate Functions ที่รวมหลายแถวเป็นค่าเดียว
  • จับคู่กับ GROUP BY เพื่อรวมตามช่วงเวลา (1 ชม. = 1 จุดกราฟ)
  • $__timeGroup(created_at, '1h') = แบ่งข้อมูลเป็นกล่องเวลา 1 ชม. แล้วคำนวณสถิติในแต่ละกล่อง
  • ดูรูปแบบ: สูงสุดช่วงไหน? กลางคืนเย็นแค่ไหน? → เอาไปตัดสินใจจริง

ตัวอย่างโค้ด

SELECT
  $__timeGroup(created_at, '1h') AS time,
  AVG(temp) AS avg_temp,
  MAX(temp) AS max_temp,
  MIN(temp) AS min_temp
FROM sensor_data
WHERE $__timeFilter(created_at)
GROUP BY 1          -- จัดกลุ่มตามช่วงเวลา 1 ชม.
ORDER BY 1;

จุดที่พลาดบ่อย

  • ใช้ aggregate โดยไม่มี GROUP BY + ไม่ครอบทุกคอลัมน์ → error
  • GROUP BY ชื่อคอลัมน์เดิมแทน GROUP BY 1 (เลขตามลำดับ) อาจเจอ warning
  • ช่วงเวลาเล็กเกินไป vs ข้อมูลน้อย → กราฟเต็มไปด้วยช่องว่าง
สีบอกสถานะ

Data Mapping & Thresholds

ตั้งเกณฑ์ให้ตัวเลขเปลี่ยนเป็นสี: เขียว = ปกติ เหลือง = ควรระวัง แดง = อันตราย อ่านง่ายในแวบเดียว

ทำ UX ที่ดีด้วยสีบอกสถานะ
เจาะลึกทางเทคนิค

ทำงานอย่างไร

  • Thresholds = จุดเปลี่ยนสีตามค่า เช่น 30°C = เขียว, 35°C = เหลือง, 40°C = แดง
  • ตั้งได้ 2 แบบ: Base (ค่าจาก 0 ขึ้นไป) หรือ Absolute (จุดจริง)
  • นอกจากสี ยัง Value Mapping แปลงตัวเลขเป็นข้อความ (0 → "ปิด", 1 → "เปิด")
  • ใช้กับ Stat Panel (การ์ดตัวเลข) หรือ Threshold ตกแต่งกราฟ (วาดเส้น/พื้นหลังสี)
  • หลัก UX: สแกนพริบตาเดียว ก็รู้ว่าระบบปกติดีหรือมีปัญหา

การตั้งค่า

Grafana Panel > Edit > Thresholds (หรือ Field/Standard options)

     0 °C - 30 °C  → สีเขียว   (ปกติ)
    31 °C - 35 °C  → สีเหลือง  (ควรระวัง)
    36 °C ขึ้นไป    → สีแดง    (อันตราย!)

Value mappings: 0 → "ปิด" , 1 → "เปิด"

จุดที่พลาดบ่อย

  • ตั้ง Threshold แบบ Absolute แต่คิดแบบ Base → สีผิดจุด
  • ลืมตั้ง Unit (เช่น °C) → ตัวเลขแสดงแบบมั่ว
  • threshold ไม่ตรงเกณฑ์ของโรงงาน/สเปคจริง → หลอกผู้ใช้ให้ตกใจหรือเมินเฉย
  • 1 เชื่อมต่อ Data Source ด้วย SSL Mode: require
  • 2 ข้อมูล Time-series = (เวลา, ค่า) + Macro $__timeFilter
  • 3 Query สถิติด้วย AVG / MAX / MIN + $__timeGroup
  • 4 Thresholds แปลงค่าเป็นสีเขียว/เหลือง/แดง

"อุณหภูมิคือ 29.5 องศา!"

เซนเซอร์อ่านค่าได้ แล้วบอร์ดห่อเป็น JSON เปิด Wi-Fi ยิง HTTP POST ไปหาเซิร์ฟเวอร์ (รอ HTTP 201) จากนั้นเข้านอน (Deep Sleep) รอรอบหน้า

"มีจดหมายเข้า!"

Express รับที่เส้นทาง /api/data middleware express.json() แกะ JSON ออกมา แล้วใช้ pool ของ PgBouncer ส่งเข้า DB แบบ async ไม่รอใคร

"เก็บเข้าชั้นหนังสือ"
